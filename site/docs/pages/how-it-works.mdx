# How it works

chronozarr is a layout convention plus readers. Every object is an ordinary Zarr
v3 object; the convention specifies a time axis, a multiscale pyramid, coordinates,
and true stored values. The v0.3 profile uses zarr-conventions multiscales, proj and spatial v0.1; volatility is optional.

## A pyramid of arrays

Each numbered group is a resolution level. Level 0 preserves the stored input
values; coarser levels contain block means. Data has dimensions `(time, band, y, x)`.
Coordinates and metadata describe its native projection.

```text
my_store/
  zarr.json             consolidated metadata and format attributes
  0/                    original resolution
    data/               time × band × y × x
    time/ band/ y/ x/    coordinate arrays
    mask/ coverage/     optional validity and observed coverage
  1/                    half resolution
  2/                    quarter resolution
```

## Random access through time

The default unsharded layout uses one object per spatial cell and timestep.
Sharding is an option when reducing object count is useful, with byte-range reads
and index caching as the tradeoff. Growing stores generally favor unsharded output:
new timesteps add objects rather than rewriting a trailing shard.

Every timestep contains true stored values. Reading one timestep of a cell needs one data chunk. v0.2 stores require explicit migration: `chronozarr convert OLD_STORE NEW_STORE`.

## Values and validity

The format supports uint8, uint16, int16, and float32. Scale and offset describe
physical values; a validity mask can distinguish valid zero from missing data.
Coverage records how much input was observed, separately from validity.

Compatible ordinary Zarr clients read true stored values. Physical units still require scale and offset.

See the [draft specification](/specification) for the normative requirements and
[format comparison](/guides/format-comparison) for alternatives.
